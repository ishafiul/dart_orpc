---
title: dart_orpc_luthor
description: Luthor schema validation bridge for typed input, output, and generated schemas.
---

This package re-exports Luthor and adapts its schema results to framework errors. With `@luthor` DTOs and `luthor_generator`, generated procedures automatically use schema validators. Freezed and json_serializable can supply immutable JSON contracts alongside them.

| Bridge | Behavior |
| --- | --- |
| `decodeRpcInputWithLuthor<T>` | Checks object input, validates, returns DTO; validation failure is BAD_REQUEST |
| `encodeRpcOutputWithLuthor<T>` | Serializes DTO, validates serialized value, returns JSON; failure is a generic INTERNAL_ERROR with a server-only diagnostic |
| `encodeRpcOutputJsonWithLuthor<T>` | Validates serialized JSON without reconstructing a DTO |
| `LuthorValidator<T>` | `ValidationResult<T> Function(Object? json)`, such as a generated `$XValidate` |
| `LuthorJsonValidator` | JSON-only validation, such as a generated schema's `validate` |

## Upgrade bridge calls to Luthor 1.1

Regenerate application code after updating both `luthor` and `luthor_generator` to 1.1. In handwritten bridge calls, replace uses of `validateReadOnly` and `LuthorReadOnlySchemaValidator` with a single `validate` callback that returns Luthor's `ValidationResult<T>`. Use the generated DTO callback or call its schema's `validateSchema(json, fromJson: Dto.fromJson)`. Validators must leave the JSON they receive unmodified.

Output bridges take `output`, `method`, and `toJson`. Pass `validate` to `encodeRpcOutputWithLuthor` or `validateJson` to `encodeRpcOutputJsonWithLuthor`.

## Unknown keys

Luthor strips undeclared keys by default. Use `@Luthor(unknownKeys: .passthrough)` to pass them to the decoder or `@Luthor(unknownKeys: .strict)` to reject them with `BAD_REQUEST` on input. An explicit DTO mode takes precedence over the `luthor_generator:luthor` `unknown_keys` builder option in the DTO package's `build.yaml` or the root package's `global_options`. Strict DTOs are documented with `additionalProperties: false`. A DTO field using `@JsonKey(readValue: ...)` fails the build because it can read keys the schema cannot describe.

For DTOs that rely on builder options, the effective mode must agree across the package's build targets and across development and release builds. Set `@Luthor(unknownKeys: ...)` explicitly on DTOs in packages that need conflicting builder options.

See [DTOs and Validation](/dart-orpc/guides/procedures-and-dtos) for a strict input DTO with a non-empty title.

Input validation issues are formatted into `error.message` as `path: message` entries joined by semicolons. Input failures also list every issue, in order, in `error.details.issues`: each has a `path` of string keys and list indexes (`[]` for the whole value), luthor's `IssueCode` name as `code` (such as `tooShort` or `unrecognizedKey`), and the `message`. Read them with `parseRpcValidationIssues`. Input that isn't a JSON object carries no issues.

Output failures are the server's bug, so clients only get `INTERNAL_ERROR` with `Internal server error.` and no details: field names and validation text stay on the server. The thrown `RpcException` carries an `RpcOutputValidationDiagnostic` in its server-only `diagnostic`, with the procedure's method and the issues but not the output payload. Server `onError` hooks receive that exception on HTTP RPC, REST, SSE and WebSocket, and its `toString()` includes the diagnostic for logs. OpenAPI components come from build-time DTO metadata.
