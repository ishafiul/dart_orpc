## RpcContext API

`RpcContext` is a concrete immutable request context. Construct it with required `headers`; optional fields are `httpMethod` (default `POST`), `path` (default `/rpc`), `attributes`, `bindings`, and `cancellation`.

| API | Purpose |
| --- | --- |
| `headers` | Immutable header map |
| `headerValue(name)` | Case-insensitive lookup |
| `httpMethod`, `path` | Transport request method and path |
| `attributes` | Immutable application attributes, `Map<String, Object?>` |
| `bindings` | Typed application state |
| `binding(key)` | Nullable lookup |
| `requireBinding(key)` | Required lookup; throws if missing |
| `copyWith(...)` | Produce a context preserving fields you do not replace |
| `cancellation` | Cooperative cancellation signal |

There is no built-in `context.auth`, `context.metadata`, or request-scoped DI container.

## Typed bindings

Define and share one key constant; key instances identify bindings:

```dart
const tenantKey = RpcContextKey<String>('app.tenant');

final app = const AppModule().buildRpcApp(
  bindings: const RpcContextBindings.empty().withValue(tenantKey, 'demo'),
);
```

Use `context.requireBinding(tenantKey)` in code that requires it. `RpcContextBindings.withValue` and `merge` create snapshots; `toBuilder()`, `set`, `addAll`, and `build` batch updates.

Application-wide bindings hold configuration and shared state. Per-request values belong in `contextFactory`:

```dart
contextFactory: (request) => RpcContext(
  headers: request.headers,
  httpMethod: request.method,
  path: request.path,
  attributes: {'clientAddress': request.remoteAddress},
),
```

The HTTP adapter merges app bindings with factory bindings and preserves the request cancellation signal. Built-in `rpcRequestIdKey` exposes correlation ID. `rpcHttpResponseKey` exposes optional HTTP response controls; use nullable lookup in transport-neutral controllers.

## Expected errors

Throw `RpcException` for expected public failures:

```dart
throw RpcException.badRequest('Title must not be empty.');
throw RpcException.notFound('Todo not found.');
throw RpcException.conflict('Version changed; reload and retry.');
```

Factories also include `unauthorized`, `forbidden`, `cancelled`, `resourceExhausted`, `internalError`, `requestTimeout`, `payloadTooLarge`, `unavailable`, and `deadlineExceeded`. The general constructor accepts an enum:

```dart
throw const RpcException(
  code: RpcErrorCode.unsupportedMediaType,
  message: 'Use application/json.',
);
```

`statusCode` comes from the code. `toResponse()` creates the public error envelope. Arbitrary string codes and custom `statusCode` arguments are not supported; attach structured context with [`details`](#error-details) instead.

| Wire code | HTTP status |
| --- | --- |
| `BAD_REQUEST` | 400 |
| `UNAUTHORIZED` | 401 |
| `FORBIDDEN` | 403 |
| `NOT_FOUND` | 404 |
| `REQUEST_TIMEOUT` | 408 |
| `CONFLICT` | 409 |
| `PAYLOAD_TOO_LARGE` | 413 |
| `UNSUPPORTED_MEDIA_TYPE` | 415 |
| `RESOURCE_EXHAUSTED` | 429 |
| `HEADERS_TOO_LARGE` | 431 |
| `CANCELLED` | 499 |
| `INTERNAL_ERROR` | 500 |
| `UNAVAILABLE` | 503 |
| `DEADLINE_EXCEEDED` | 504 |

Client code can compare `error.code == RpcErrorCode.notFound` and inspect `error.message`. Unexpected transport/protocol failures use `RpcClientException`. Log original server exceptions through [`serverOptions.onError`](#observing-errors-with-onerror); keep exception text, credentials, and internals out of public errors.

## Error details

Attach optional structured context to an error with `details`, a JSON object:

```dart
throw RpcException.conflict(
  'Version changed; reload and retry.',
  details: {'currentVersion': 3},
);
```

Every factory accepts `details:` except `cancelled` and `internalError`, whose message is an optional positional argument. For those, use the constructor:

```dart
throw const RpcException(
  code: RpcErrorCode.internalError,
  message: 'Export failed.',
  details: {'jobId': 'export-42'},
);
```

Every transport sends the same `error` object, with `details` next to `code` and `message`:

```json
{"error": {"code": "CONFLICT", "message": "Version changed; reload and retry.", "details": {"currentVersion": 3}}}
```

That object is the body of `POST /rpc` and REST error responses, the `data` of the SSE `dart-orpc-error` event, and the `error` of WebSocket `error` frames. Null or empty details are left out, so errors without details look exactly as before.

Rules:

- **Details are client-visible.** Never put secrets, credentials, stack traces, or internal diagnostics in them.
- **`issues` is reserved.** The `details.issues` key is reserved for framework validation issues; don't use it for your own data.
- **Values are normalized like procedure outputs.** Objects with `toJson()` are converted, so DTOs can go inside details.
- **Encoding never hides the error.** If details contain a cycle or a value that can't be converted to JSON, the client still receives the real `code` and `message`, without details, and the server reports an `RpcErrorDetailsEncodingException` through `onError`.
- **WebSocket frames stay within `maxFrameBytes`.** An error frame that is too large is re-sent without details; the connection stays open. See [WebSocket Streaming](/dart-orpc/guides/websocket-streaming#errors).

Read details from the `RpcException` the client throws:

```dart
try {
  await client.todo.update(input);
} on RpcException catch (error) {
  if (error.code == RpcErrorCode.conflict) {
    final currentVersion = error.details?['currentVersion'];
    // Reload and retry with currentVersion.
  }
}
```

`HttpRpcTransport` sets `details` on the `RpcException` it throws for unary calls. `WebSocketRpcTransport` sets them for unary calls and for errors emitted by streams. In both, a missing value, or one that is not a JSON object, gives `null`; the code and message are kept. Details are an untyped `JsonObject`.

## Observing errors with onError

`RpcHttpServerOptions.onError` is the single error hook for HTTP and WebSocket. Each `RpcHttpErrorEvent` carries the original `error` and `stackTrace`, the `request`, and:

| Field | Meaning |
| --- | --- |
| `transport` | `RpcTransportKind.http` (RPC, REST, SSE) or `RpcTransportKind.webSocket` |
| `rpcMethod` | The failed call's RPC method, when known (WebSocket) |
| `callId` | The WebSocket call id, when known |

```dart
final app = const AppModule().buildRpcApp(
  serverOptions: RpcHttpServerOptions(
    onError: (event) {
      if (event.transport == RpcTransportKind.webSocket) {
        log.severe(
          'WebSocket ${event.rpcMethod} (call ${event.callId}) failed',
          event.error,
          event.stackTrace,
        );
      } else {
        log.severe(
          '${event.request.method} ${event.request.path} failed',
          event.error,
          event.stackTrace,
        );
      }
    },
  ),
);
```

This fragment assumes an application `log`. What gets reported differs by transport:

- **HTTP** (RPC, REST, SSE): errors thrown while handling a request, by procedures, guards, validation, or the framework (rate limiting included), are reported, including `RpcException`s. That's at most once per request, plus an `RpcErrorDetailsEncodingException` if the error's details had to be dropped. Sending an HTTP error response doesn't by itself trigger `onError`: responses the adapter returns directly, such as `405 Method Not Allowed` for a wrong HTTP method or a rejected CORS preflight, aren't reported.
- **WebSocket**: only unexpected failures that are not `RpcException`s (the client receives `INTERNAL_ERROR`) and the details and frame-size fallbacks are reported. An `RpcException` is sent to the client without an `onError` event. A connection can report any number of errors.

The hook runs synchronously; an exception it throws is contained and does not affect the response.

## Cancellation

`RpcCancellationSource` owns cancellation; pass its `.signal` to work and call `.cancel()` to notify listeners. The signal provides `isCancelled`, `cancelled`, `throwIfCancelled()`, and the `onCancel` extension.

```dart
final registration = context.cancellation.onCancel(cancelDownstreamWork);
try {
  context.cancellation.throwIfCancelled();
  return await runWork();
} finally {
  registration.dispose();
}
```

This fragment assumes application callbacks. Cancellation is cooperative: it cannot forcibly stop an arbitrary Dart `Future`. Propagate it to database/HTTP/job APIs that support cancellation, and stop stream subscriptions during cleanup.

WebSocket subscription cancellation sends a cancel frame. HTTP I/O disconnects and shutdown deadlines cancel tracked work. SSE heartbeats help detect idle disconnects. `handlerTimeout` bounds response creation, not the lifetime of an already returned stream.
