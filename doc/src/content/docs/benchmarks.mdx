## Results

| # | Server | Req/s | Range | p99 | Peak RAM |
| ---: | --- | ---: | --- | ---: | ---: |
| 1 | hyper 1.12 | 288,141 | 287k–290k | 1 ms | 4 MiB |
| 2 | **rust_http** | **278,150** | 258k–279k | 2 ms | 13 MiB |
| 3 | Bun 1.4.4 | 267,440 | 261k–270k | 1 ms | 88 MiB\* |
| 4 | **dart_orpc** | **138,272** | 135k–140k | **3 ms** | 36 MiB |
| 5 | dart:io | 56,126 | 55k–56k | 6 ms | 22 MiB |
| 6 | Shelf 1.4.3 | 46,645 | 46k–47k | 8 ms | 41 MiB |
| 7 | Dart Frog 1.2.6 | 37,288 | 36k–38k | 9 ms | 44 MiB |
| 8 | Serverpod 4.0.4 | 33,436 | 33k–34k | 10 ms | 54 MiB |

Req/s is the median of three rounds, and Range is the lowest to highest round. p99 is the 99th-percentile latency in the median round. Peak RAM is the highest container memory seen in any round.

\* Bun reached 88 MiB only in its first round and used about 4 MiB in the other two.

No server returned errors, timeouts or non-2xx responses.

## What the numbers say

- **dart_orpc is the fastest Dart framework here**: 2.5× raw `dart:io`, 3× Shelf, 3.7× Dart Frog and 4.1× Serverpod, with the lowest p99 of the Dart frameworks (3 ms).
- **It does more work than the others for this response.** The route is a real `@Controller` method with `@RpcMethod(path: RestMapping.get('/'))`, going through routing, the request context, cancellation, middleware and JSON encoding. It returns the JSON string `"Hello, World!"` with `application/json` and a request ID header; the other servers send plain text.
- **rust_http is where the headroom comes from.** Rust owns the sockets and parses HTTP, and hands each request to Dart through the `dart:io` API. On its own it runs alongside hyper and Bun. dart_orpc keeps about half of that throughput; the other half is the framework's own Dart work per request.
- **Rows 1–3 are effectively a tie.** At this rate the load generator is close to its own limit, so small differences between them are not meaningful.
- **Memory stays modest.** dart_orpc peaked at 36 MiB. Dart's memory grows with the number of requests in flight, not with request rate: at 16 connections it uses about 5 MiB.

## Method

- **Machine:** Docker on an Apple Silicon Mac (linux/arm64 containers), all on one host. Server and load generator run in separate containers.
- **Server container:** pinned to one CPU core with `--cpuset-cpus 0 --memory 2g`. Each round starts a fresh container.
- **Load:** [autocannon](https://github.com/mcollina/autocannon) 9.0.0 with 256 connections and 4 workers on 8 other cores, over a private Docker network.
- **Timing:** 5 seconds of warm-up, then 20 seconds measured. Three rounds, with every server run once per round in rotation.
- **Dart servers:** one isolate each, AOT-compiled on Dart 3.14.0. dart_orpc uses its default options. Serverpod runs in production mode with session logging off, called at `/hello/world` because its `GET /` is the built-in health check.
- **Others:** hyper uses the default tokio runtime (one worker on one core). Bun uses `Bun.serve`.
- **Memory:** the peak of one-second `docker stats` samples during the measured window. It is container memory, not process RSS.

Treat these as relative numbers: the client shares the host with the server, and Docker Desktop runs a VM. A hello-world route measures the cost of the server and framework, not of your application code. Database calls, validation and real payloads will dominate real endpoints.

## Run it yourself

The dart_orpc server is a normal generated app with one controller:

```dart
@Module(controllers: [HelloController])
final class HelloModule {
  const HelloModule();
}

@Controller('hello')
final class HelloController {
  const HelloController();

  @RpcMethod(path: RestMapping.get('/'))
  String hello() => 'Hello, World!';
}
```

Generate it with `dart run build_runner build`, build it with `dart build cli`, and serve it with `const HelloModule().buildRpcApp().listen(8080, hostname: '0.0.0.0')`. Then load it the same way as above:

```sh
docker run --rm --cpuset-cpus 0 --memory 2g -p 8080:8080 <server-image>
npx autocannon -c 256 -w 4 -d 20 http://127.0.0.1:8080/
```

Run a 5-second warm-up before each measured run, and alternate servers between rounds so that changes in machine load affect them equally.
